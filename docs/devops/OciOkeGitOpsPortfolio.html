OCI OKE 프로덕션 GitOps 포트폴리오

홈랩 k3s에서 검증하고 Oracle Kubernetes Engine으로 승격하는 운영 파이프라인

저자

배진후

1 핵심 요약

Production

Oracle Kubernetes Engine을 프로덕션 클러스터로 잡고 kubeconfig, 접근 권한, 스토리지, 관측성을 구성

GitOps

mintcocoa-ops 저장소를 OKE 중심으로 재작성하고 Argo CD Application 구조로 desired state를 선언

Pipeline

홈랩 k3s를 staging/dev 환경으로 두고 검증 후 OKE production overlay로 승격

Operate

Prometheus, Grafana, Loki, Promtail, Tempo, metrics-server를 설치하고 실제 API 응답까지 검증

2 프로젝트 배경

DevOps 포트폴리오에서 보여주고 싶었던 것은 단순히 Kubernetes를 사용했다는 사실이 아니라, 클러스터를 직접 연결하고, 운영 기준을 정하고, 배포 흐름을 Git으로 관리할 수 있게 만든 과정입니다.

기존에는 홈랩 중심의 Kubernetes/GitOps 실험이 있었고, 새로 OCI OKE 클러스터를 프로덕션 기준 환경으로 잡았습니다. 이후 홈랩 k3s는 staging/dev 역할로 남기고, OKE는 production 역할로 분리했습니다.

4 인프라 구축 과정

처음에는 로컬 kubeconfig가 다른 클러스터를 가리키고 있어 OKE API에 바로 접근할 수 없었습니다. OCI CLI로 클러스터를 조회하고, OKE public endpoint를 사용하는 kubeconfig를 새로 생성해 기본 kubectl 컨텍스트를 교체했습니다.

확인 항목 결과
OCI CLI 인증 정상
OKE cluster home-oci-oke-cluster
API endpoint https://168.110.124.39:6443
Node 상태 arm64 worker node 3개 Ready
Kubernetes version v1.33.1

외부 모바일/GUI 클라이언트처럼 OCI CLI exec 인증을 실행할 수 없는 경우를 위해 ServiceAccount 기반 정적 kubeconfig도 만들었습니다. 다만 이 방식은 권한이 강할수록 위험하므로, Git에는 토큰을 저장하지 않고 폐기 명령까지 runbook에 남겼습니다.

5 배포 자동화 방식

운영 저장소는 OKE production을 중심으로 다시 구성했습니다.

mintcocoa-ops/
  bootstrap/
    oke-prod-root.yaml
    home-root.yaml
  clusters/
    oke-prod/
    home/
  apps/
    dropapp/
      base/
      overlays/home/
      overlays/oke-prod/
    whoami/
      base/
      overlays/home/
      overlays/oke-prod/
  infrastructure/
    kubernetes/cluster-issuers/
    kubernetes/grafana-datasources/
  docs/
    runbooks/

공통 앱은 base에 두고, 환경별 차이는 overlay에 둡니다.

apps/<app>/base
  -> apps/<app>/overlays/home
  -> apps/<app>/overlays/oke-prod

GitHub Actions는 PR이나 main push 때 다음을 검증합니다.

  1. clusters/home 렌더링
  2. clusters/oke-prod 렌더링
  3. apps/whoami/overlays/home와 apps/whoami/overlays/oke-prod 렌더링
  4. apps/dropapp/overlays/home와 apps/dropapp/overlays/oke-prod 렌더링
  5. cluster-issuers, Grafana datasource 렌더링
  6. 민감정보 패턴 검사

production 반영은 Promote home overlay to OKE 수동 workflow로 분리했습니다. 홈랩에서 먼저 검증하고, 같은 이미지 태그를 OKE overlay에 반영하는 구조입니다.

6 대표 워크로드: RuntimeWeb dropapp

whoami는 파이프라인 증명용으로 남겨두고, 실제 포트폴리오 대표 앱은 iouring-runtime의 dropapp으로 잡았습니다. dropapp은 C++ RuntimeWeb 위에서 동작하는 TTL 파일 전송 앱입니다. 단순 hello world보다 포트폴리오에서 보여줄 수 있는 운영 표면이 넓습니다.

항목 구성
이미지 ghcr.io/mint-cocoa/dropapp:<git-sha>
Home 검증 home-services, NodePort 30081
OKE 공개 prod-services, Ingress drop.mintcocoa.cc
쓰기 권한 DROPAPP_AUTH_TOKEN bearer token Secret
저장 정책 emptyDir 1Gi, DROPAPP_DEFAULT_TTL_SECONDS=3600
최대 업로드 DROPAPP_MAX_UPLOAD_BYTES=104857600

이 앱은 RuntimeWeb 문서에서 설명한 streaming upload, static file response, route parameter, token-protected write path, timeout/backpressure 설정을 실제 서비스 매니페스트로 연결합니다. 즉 서버 구현 포트폴리오와 DevOps 포트폴리오가 분리된 글이 아니라 하나의 배포 사례로 이어집니다.

OKE 공개 경로는 ingress-nginx와 cert-manager를 GitOps Application으로 관리하고, letsencrypt-prod ClusterIssuer로 TLS 인증서를 발급하는 구조입니다.

7 관측성 구성

OKE 클러스터에는 운영 확인을 위해 다음 스택을 구성했습니다.

구성요소 역할
metrics-server kubectl top과 기본 리소스 메트릭
Prometheus cluster/workload metrics 수집
Grafana dashboard와 datasource 통합
Alertmanager 알림 경로 준비
Loki 로그 저장
Promtail node log shipping
Tempo trace ingest/query 준비

설치 후 단순히 Pod가 떴는지만 본 것이 아니라, 실제 API 응답까지 확인했습니다.

kubectl top nodes                 # 성공
Prometheus /api/v1/query?query=up # 성공
Loki /loki/api/v1/labels          # 성공
Tempo /ready                      # ready

OCI Block Volume은 최소 프로비저닝 단위 때문에 요청값보다 큰 50Gi PVC가 생성되는 특성이 있었습니다. 이 점은 GitOps values와 운영 문서에 반영했습니다.

8 장애 대응 및 운영 판단 사례

상황 원인 조치
기본 kubeconfig 접속 실패 기존 context가 172.30.1.27:6443 내부 주소를 바라봄 OCI OKE public endpoint kubeconfig 생성 후 기본 context 교체
외부 클라이언트 인증 제약 모바일 앱은 oci ce cluster generate-token 실행 불가 ServiceAccount token 방식 kubeconfig 별도 생성
Bastion 경로 오해 가능성 WireGuard VM은 있었지만 OKE VCN과 peering/route 없음 public OKE endpoint를 기준 접근 경로로 문서화
Loki 기본값 과다 기본 cache 설정이 작은 클러스터에 과함 SingleBinary, cache 비활성화, 제한된 retention으로 조정
Grafana password 평문 위험 초기 values에 임시 비밀번호가 남을 수 있음 Kubernetes Secret 참조 방식으로 전환
공개 업로드 악용 가능성 파일 전송 앱을 인터넷에 공개하면 쓰기 경로가 공격 표면이 됨 업로드/삭제는 bearer token으로 보호하고 파일은 TTL과 emptyDir 크기 제한으로 회수

이 과정에서 운영 기준도 함께 정했습니다.

  • production 서비스는 홈랩에 의존하지 않는다.
  • 홈랩은 staging/dev와 복구 연습 환경으로 둔다.
  • OKE Argo CD가 home k3s를 원격 관리하는 구조를 목표로 한다.
  • 토큰, kubeconfig, Grafana 비밀번호는 Git에 저장하지 않는다.
  • 외부 공개는 명시적으로 필요한 앱만 Ingress로 열고, 쓰기 권한은 Secret 기반으로 둔다.

11 면접에서 설명할 포인트

이 프로젝트는 완성된 SaaS 운영팀 수준의 대규모 플랫폼이라기보다, 작은 클러스터에서 운영자가 직접 결정해야 하는 문제를 끝까지 다룬 사례입니다.

  • 어떤 endpoint를 production 접근 기준으로 삼을지 결정
  • 어떤 인증 방식이 사람/자동화/모바일 클라이언트에 맞는지 구분
  • 기본 Helm chart 값을 그대로 쓰지 않고 클러스터 크기에 맞게 조정
  • GitOps repo를 기존 kubeadm cloud 기준에서 OKE production 기준으로 재작성
  • home과 production을 섞지 않고 promotion 흐름으로 분리
  • 직접 만든 io_uring 기반 앱을 컨테이너, GitOps, Ingress, TLS, 로그/메트릭까지 연결
