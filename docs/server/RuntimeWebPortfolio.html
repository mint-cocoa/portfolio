2 모듈 개요

RuntimeWeb은 iouring-runtime의 기본 Runtime 위에 붙인 HTTP 서버 모듈입니다. 서비스 앱 자체가 아니라, HTTP 애플리케이션을 만들 때 반복되는 parser, router, request/response, 정적 파일 응답, streaming body, timeout, backpressure 처리를 묶은 선택형 라이브러리 계층입니다.

중요한 기준은 HTTP 모듈이 accept, recv, send, buffer pool, 세션 수명관리를 새로 만들지 않는다는 점입니다. 새 연결은 여전히 코어 Worker와 Listener가 받고, 실제 소켓 I/O는 코어 Session의 Multishot Recv, Provided Buffer, send queue, timeout 경로를 그대로 사용합니다. RuntimeWeb은 그 위에서 TCP byte stream을 HTTP request로 해석하고, route handler의 응답을 다시 코어 send queue에 싣는 역할만 맡습니다.

3 구성 요소

3.1 WebServer — 코어 Worker를 HTTP 서버로 감싸기

WebServer는 앱이 직접 WorkerConfig, SessionFactory, HttpSession 생성 코드를 매번 작성하지 않도록 만든 wrapper입니다. 앱은 server.Get(), server.Post(), server.PutStream() 같은 API로 route만 등록하고, Start()를 호출합니다.

내부적으로 WebServer::Start()는 worker 수만큼 코어 Worker를 만들고, 각 worker의 SessionFactory가 HttpSession을 생성하도록 연결합니다. 이때 WebServerConfig의 parser option, request timeout, inactivity timeout, send queue watermark, recv pause 정책이 세션에 주입됩니다.

src/modules/web/WebServer.cpp — HttpSession 생성 흐름 요약
auto factory = [router, parser_options, timeouts, backpressure, raw_worker](
    int fd, IoRing& ring, BufferPool& pool, ContextId shard_id) {
    auto session = std::make_shared<HttpSession>(
        fd, ring, pool, *router,
        backpressure.send_queue_max_pending,
        parser_options,
        timeouts.request,
        shard_id);

    session->SetInactivityTimeout(timeouts.inactivity);
    session->SetBackpressureWatermarks(...);
    session->SetPauseRecvOnBackpressure(...);
    return session;
};

즉 HTTP 서버가 되어도 core Runtime의 흐름은 유지됩니다. accept는 Listener, recv는 Session::RegisterRecv(), 송신은 Session::Send(), 종료는 Disconnect()와 drain timeout 정책을 그대로 탑니다.

3.2 HttpSession — TCP stream을 HTTP request로 변환

HttpSession은 core::io::Session을 상속합니다. 코어가 OnRecv(std::span<const std::byte>)를 호출하면, HttpSession은 받은 바이트를 HttpParser에 공급합니다. parser는 header 완료 시점에 body 처리 방식을 결정하고, 요청이 완성되면 Router로 dispatch합니다.

이 구조에서 HttpSession이 직접 담당하는 일은 네 가지입니다.

  • 수신 byte stream을 HTTP request 단위로 자르기
  • request timeout과 inactivity timeout을 구분하기
  • route handler가 만든 응답을 코어 send queue에 싣기
  • 파일/streaming 응답처럼 여러 send buffer가 필요한 응답을 세션 수명 안에서 이어 보내기

3.3 Router와 RadixTree — 앱 분기를 모듈로 고정

라우팅은 앱마다 if (path == ...)를 반복하지 않도록 Router에 모았습니다. Router는 HTTP method별 handler와 streaming handler를 등록하고, 실제 path match는 RadixTree가 담당합니다.

지원하는 route 형태는 정적 경로, :param, *wildcard입니다. 예를 들어 GET /hello/:name, GET /files/*path, DELETE /api/files/:id 같은 형태를 같은 자료구조에서 처리합니다. match 결과는 HttpRequest::Param()과 ParamDecoded()로 handler에 노출됩니다.

Use() middleware는 route handler 이전에 실행됩니다. 인증, request id header, 공통 CORS 처리처럼 앱마다 반복되는 전처리를 handler 바깥으로 뺄 수 있습니다. handler가 이미 응답을 보냈다면 이후 route 처리는 진행하지 않는 식으로 요청 수명을 끊을 수 있습니다.

3.4 HttpResponse — 응답 조립과 전송 경계

HttpResponse는 status line, header, body를 조립하고 HttpSession에 전송을 위임합니다. 앱 handler는 Text(), Json(), Error(), Header(), Status(), Body(), Send() 같은 API로 응답을 구성합니다.

파일 응답은 HttpResponse::SendFile()을 통해 별도 경로로 빠집니다. 모듈은 파일 크기와 content type을 확인하고, 세션의 file 전송 경로가 buffer를 할당해 send queue에 차례로 넣습니다. 이 덕분에 작은 JSON 응답과 정적 파일 응답이 같은 route API 위에 있지만, 내부 전송 방식은 응답 크기와 종류에 맞게 분리됩니다.

4 Streaming Body와 파일 응답

RuntimeWeb에서 중요한 구현 지점은 대용량 요청/응답을 HttpRequest::body 하나에 모두 쌓지 않는 것입니다. 일반 JSON API는 request body를 문자열로 모아도 충분하지만, 파일 업로드나 speed test traffic은 body 전체를 메모리에 들고 있으면 느린 클라이언트 하나가 worker의 메모리를 오래 점유합니다.

이를 위해 Router는 일반 route와 별도로 streaming route를 제공합니다.

file_store_server는 PUT /api/files/*path에서 이 경로를 사용해 업로드 chunk를 .part 파일로 바로 기록합니다. dropapp은 POST /api/files에서 TTL 파일 drop 저장소로 body를 흘려보냅니다. 두 앱은 서비스 기능은 다르지만, 검증하는 모듈 표면은 동일합니다. body를 앱 메모리에 누적하지 않고 parser callback에서 chunk 단위로 처리하는 RuntimeWeb의 streaming route입니다.

응답 쪽에서는 SendFile()과 직접 buffer 전송이 나뉩니다. 정적 파일이나 다운로드 파일은 SendFile() 경로로, speedtest_server처럼 생성 payload를 반복 전송하는 경우는 BufferPool에서 chunk buffer를 확보해 ctx.session.SendResponse()로 보냅니다. 어느 쪽이든 최종 send는 코어 Session의 send queue, short write retry, backpressure 정책을 공유합니다.

5 Timeout과 Backpressure

HTTP 서버는 느린 클라이언트와 큰 응답을 함께 다뤄야 하므로, RuntimeWeb은 코어 Session의 정책을 HTTP 설정으로 노출했습니다.

request timeout은 HTTP 요청 하나가 너무 오래 열려 있는 상황을 끊기 위한 정책이고, inactivity timeout은 연결 자체가 idle 상태로 오래 유지되는 상황을 끊기 위한 정책입니다. 둘 다 최종적으로는 코어 timeout event와 Session 종료 경로를 사용하지만, HTTP 모듈에서는 의미를 분리해 설정합니다.

backpressure는 응답을 보내는 속도보다 handler가 send buffer를 더 빨리 쌓는 상황을 제어합니다. high watermark를 넘으면 세션은 backpressure active 상태가 되고, 설정에 따라 recv를 잠시 멈추거나 일정 시간 뒤 연결을 끊습니다. low watermark 아래로 내려가면 다시 정상 수신으로 돌아옵니다. 이 정책은 Web 전용 구현이 아니라 코어 Session의 공통 기능을 WebServerConfig로 드러낸 것입니다.

6 소비 앱의 역할

RuntimeWeb 문서에서 예제 앱은 구현의 중심이 아니라 모듈 검증 표면입니다. 각 앱은 서로 다른 기능을 보여주지만, 모두 같은 HTTP 세션, 라우터, 응답 전송, backpressure 경로를 사용합니다.

이 구분을 유지하면 포트폴리오에서 설명해야 할 구현 단위가 명확해집니다. dropapp이나 webhook_inbox는 서비스 기능을 설명하는 이름이고, 서버 구현 포트폴리오에서 중요한 것은 그 앱들이 공통으로 링크하는 RuntimeWeb 모듈입니다.
