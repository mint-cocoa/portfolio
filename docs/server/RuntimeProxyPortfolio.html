2 모듈 개요

RuntimeProxy는 기본 Runtime 위에 붙인 TCP reverse proxy 모듈입니다. HTTP request/response 객체를 만들지 않고, downstream 클라이언트와 upstream 서버 사이의 byte stream을 직접 중계합니다. 서비스 앱인 tcp_reverse_proxy는 이 모듈을 실행하는 얇은 entrypoint이고, 구현 단위는 RuntimeProxy 라이브러리입니다.

RuntimeProxy의 핵심은 프로토콜을 해석하지 않는다는 점입니다. HTTP 서버 모듈과 달리 router나 request body 개념이 없고, 양쪽 TCP 세션의 수신 데이터를 반대편 send queue로 전달합니다. 이 때문에 웹 앱 게이트웨이뿐 아니라 TLS passthrough 성격의 stream proxy, 내부 서비스 라우팅, 운영용 edge proxy 같은 역할에 맞습니다.

3 구성 요소

4 연결 수명과 Bridge

클라이언트가 downstream listener에 접속하면 TcpProxyServer는 먼저 downstream proxy session을 만들고, 같은 worker의 ring 위에서 upstream connect를 시작합니다. connect가 성공하면 upstream session이 생성되고, 두 peer는 하나의 ProxyBridge를 공유합니다.

ProxyBridge는 peer 두 개를 서로 알게 하는 중간 객체입니다. downstream에서 받은 bytes는 upstream으로, upstream에서 받은 bytes는 downstream으로 전달합니다. 어느 한쪽이 끊기면 pair 전체를 닫아 반쪽짜리 연결이 오래 남지 않게 합니다.

upstream connect가 아직 끝나기 전에 downstream data가 들어올 수 있습니다. 이때 ProxyBridge는 설정된 pending buffer limit 안에서 upstream으로 보낼 데이터를 잠시 보관하고, connect 성공 후 FlushPendingToUpstream()으로 흘려보냅니다. limit을 넘으면 연결을 닫아 느리거나 실패한 upstream이 downstream 메모리를 무제한 점유하지 못하게 합니다.

5 TLS 종료와 SNI 라우팅

RuntimeProxy는 downstream TLS 종료를 모듈 안에 포함합니다. certificate chain과 private key는 TcpProxyConfig::DownstreamTlsOptions로 들어오고, DownstreamTlsContext가 OpenSSL context를 구성합니다. 예제 entrypoint는 signal reload 요청을 받으면 ReloadDownstreamTlsContext()를 호출해 인증서 교체를 반영합니다.

TLS 세션에서는 handshake 중 SNI hostname을 읽고, TcpProxyServer의 upstream route table에서 매칭되는 endpoint를 선택합니다. route가 없으면 default upstream으로 연결합니다. 이 경계 덕분에 앱은 hostname -> upstream host:port 정책만 설정하고, 실제 TLS handshake와 bridge 생성은 모듈이 처리합니다.

6 Timeout, Backpressure, Shutdown

Proxy 모듈은 Web 모듈처럼 코어 Session의 timeout/backpressure 기능을 설정으로 노출합니다. 차이는 HTTP request 단위가 아니라 stream 연결 단위로 동작한다는 점입니다.

backpressure는 proxy에서 특히 중요합니다. upstream이 느린데 downstream에서 계속 데이터가 들어오면 proxy가 중간 버퍼처럼 커질 수 있습니다. ProxyBridge와 peer session은 send queue watermark를 보고 반대편 recv를 pause하거나, 오래 지속되면 연결 쌍을 닫습니다. 이 정책은 core Session의 send queue와 paused recv queue 위에서 동작합니다.

7 Metrics와 운영 표면

TcpProxyServer는 런타임 상태를 JSON snapshot과 Prometheus textfile 형태로 출력합니다. worker 수, live session/connector 수, route 설정, TLS 상태, upstream connect result, backpressure transition 같은 값을 별도 metrics writer thread가 주기적으로 파일에 씁니다.

이 방식은 proxy 자체가 HTTP metrics endpoint를 열지 않아도, status_server나 node exporter textfile collector가 파일을 읽어 운영 화면에 붙일 수 있다는 장점이 있습니다. 실제 저장소의 status_server는 /run/iouring-runtime/tcp_reverse_proxy.metrics.json을 읽어 proxy 상태를 표시하는 소비자 역할을 합니다.

8 소비 앱의 역할

tcp_reverse_proxy 예제 앱은 RuntimeProxy를 검증하는 entrypoint입니다. 환경 변수에서 listen 주소, upstream, route file, TLS certificate/key, metrics path, backpressure 설정을 읽고 TcpProxyServer와 AcmeHttpChallengeServer를 실행합니다.

9 본문 문서와의 관계

이 문서는 서버 런타임 본문에서 분리한 Proxy 모듈 상세 설명입니다. 코어 io_uring 엔진, 세션 수명관리, provided buffer, MSG_RING, 벤치마크는 본문 문서에서 다룹니다.
