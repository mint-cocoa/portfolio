RuntimeGame 모듈 구현 포트폴리오

io_uring Runtime 위에 분리한 C++ packet session과 Room 실행 계층

저자

배진후

1 핵심 요약

PacketSession

TCP stream 위에서 [size:uint16][msgId:uint16] binary packet framing을 처리

Room

Room을 JobQueue로 만들어 게임 로직을 직렬 실행하고 worker 간 작업을 분배

2 모듈 개요

RuntimeGame은 기본 Runtime 위에 붙인 게임 서버용 선택 모듈입니다. 게임 콘텐츠, 전투 규칙, DB, 인증, 던전 생성 전체를 포함하는 엔진이 아니라, 네트워크 게임 서버에서 반복되는 packet framing, player registry, room lifecycle, room job queue 실행 모델을 묶은 라이브러리 계층입니다.

RuntimeGame의 기준은 게임 도메인을 코어 런타임에서 분리하는 것입니다. 코어 Runtime은 socket I/O, buffer, session lifecycle, worker, timer, queue만 담당합니다. RuntimeGame은 그 위에서 packet 단위 수신과 Room 단위 직렬 실행 모델을 제공하고, 실제 인증/전투/채팅/던전/DB는 소비 앱이 구현합니다.

3 구성 요소

4 PacketSession과 패킷 경계

TCP는 message boundary가 없는 stream이므로 게임 패킷은 여러 recv CQE에 나뉘어 도착할 수 있습니다. PacketSession은 코어 Session::OnRecv()에서 받은 bytes를 내부 RecvBuffer에 누적하고, 완전한 패킷이 만들어졌을 때만 OnPacket(packet_id, payload)를 호출합니다.

패킷 header는 little-endian uint16 두 개입니다.

이 경계를 모듈에 둔 이유는 코어 Session이 게임 프로토콜을 몰라야 하기 때문입니다. RuntimeWeb이 HTTP parser를 코어 밖에 둔 것처럼, RuntimeGame도 packet framing을 코어 밖에 둡니다. 코어 입장에서는 여전히 bytes를 받고 bytes를 보내는 TCP 세션이고, 게임 모듈만 그 bytes를 packet으로 해석합니다.

PacketBuilder는 반대 방향을 담당합니다. payload 크기와 message id를 받아 header를 붙이고, 코어 BufferPool에서 할당한 send buffer에 기록합니다. 그래서 소비 앱은 protobuf message를 직렬화한 뒤 SendPacket()을 호출하면 되고, send queue와 partial send 처리는 코어 Session에 남습니다.

5 Room과 JobQueue 실행 모델

Room은 RoomLike이면서 코어 JobQueue를 상속합니다. 이 설계의 목적은 Room 내부 게임 상태를 여러 worker가 동시에 만지지 않도록 하는 것입니다. 외부 세션이 패킷을 받으면 Room에 job을 push하고, 실제 게임 로직은 GlobalQueue에서 꺼내진 Room job queue가 직렬로 실행합니다.

Room이 JobQueue 위에 있기 때문에 얻는 효과는 세 가지입니다.

  • 같은 Room 안의 player list, position, combat state는 한 번에 하나의 worker에서만 갱신됩니다.
  • 서로 다른 Room은 GlobalQueue를 통해 여러 worker에 분산될 수 있습니다.
  • deadline 기반 Execute()를 사용하면 한 Room이 worker를 오래 독점하지 않고 다시 queue에 등록될 수 있습니다.

RuntimeGame의 Room은 구체적인 전투나 던전 규칙을 알지 않습니다. player add/remove, packet enqueue, Room id/name 같은 실행 단위만 제공합니다. dungeon_full_server는 이 Room을 상속하거나 감싸서 던전 생성, projectile, combat, chat, party 같은 도메인 기능을 얹습니다.

6 PlayerRegistry와 RoomManager

PlayerRegistry는 player가 어느 Room에 속하는지, 어떤 RoomLike와 연결되는지 추적하는 작은 registry입니다. RoomManager는 GlobalQueue를 받아 Room을 만들고, id 기준 검색과 목록 조회를 제공합니다.

이 계층은 게임 서버의 lobby, room list, matchmaking, instance dungeon 같은 구조를 만들 때 반복되는 최소 상태입니다. DB나 인증 결과를 직접 저장하지 않고, 네트워크 세션과 Room 실행 단위를 이어주는 runtime-side registry로만 남겼습니다.

7 소비 앱의 역할

RuntimeGame의 소비 앱은 모듈의 packet/room 경계가 실제 게임 서버 형태에서도 동작하는지 보여주는 검증 표면입니다.

dungeon_full_server에는 인증, 캐릭터, Room 생성/입장, 절차적 던전, 전투, 투사체, 채팅, 파티, 인벤토리 일부, SQLite/Memory DB 백엔드가 들어 있습니다. 하지만 포트폴리오에서 RuntimeGame 구현으로 설명할 부분은 이 도메인 기능 전체가 아니라, 이 기능들이 공통으로 올라탄 packet session과 Room job queue 경계입니다.

8 Web/Proxy 모듈과의 차이

세 선택 모듈은 모두 기본 Runtime 위에 올라가지만, 추상화하는 프로토콜 경계가 다릅니다.

이 비교가 중요한 이유는 코어 Runtime이 특정 앱 형태로 굳지 않았다는 점을 보여주기 때문입니다. 같은 accept/recv/send/session lifecycle 위에서 HTTP 서버, TCP proxy, packet game server가 서로 다른 모듈로 분리됩니다.

이 문서는 서버 런타임 본문에서 분리한 Game 모듈 상세 설명입니다. 코어 io_uring 엔진, 세션 수명관리, GlobalQueue와 JobQueue 자체의 구현, 벤치마크는 본문 문서에서 다룹니다.
